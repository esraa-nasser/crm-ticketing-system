# Spec-driven development with SquadKit

This repository uses [squad-kit](https://github.com/AzmSquad/squad-kit) to run a
three-step loop: **intake → plan → implement**. The point of the split is cost
and consistency — one expensive planning pass produces a concrete artifact that a
cheaper model (or a different engineer) can execute repeatedly without re-deriving
context.

## One-time setup

```bash
npm install -g squad-kit     # requires Node 18+
squad doctor                 # verifies the .squad/ workspace in this repo
```

The workspace is already initialised. `squad init` does **not** need to be run again.

Current configuration (`.squad/config.yaml`):

| Setting | Value |
|---|---|
| Project | CRM Ticketing System |
| Primary language | C# |
| Tracker | `github` |
| Agents | `claude-code`, `copilot` |
| Naming | global sequence, tracker id included in filenames |

### Optional: direct planner API

By default plans are generated by pasting a composed prompt into your agent.
To generate them straight from the terminal instead:

```bash
squad config set          # choose "planner", pick anthropic | openai | google
squad new-plan --api .squad/stories/<feature>/<id>/intake.md
```

Credentials go to `.squad/secrets.yaml`, which is git-ignored. `config.yaml`
rejects any key matching `apiKey`, `token`, `secret`, or `credential`, so a
misplaced key cannot be committed by accident.

### Optional: switch the tracker to Jira

```bash
squad config set          # choose "tracker" → jira, then supply host + credentials
squad new-story tickets --id CRM-123      # auto-fetches title, description, attachments
```

## The loop

### 1. Intake — cheap, human, ~2 KB

```bash
squad new-story <feature-slug> --id <TRACKER-ID> --title "Short title"
```

Creates `.squad/stories/<feature-slug>/<id>/intake.md`. Fill in:

- **Title** and **Description**, pasted verbatim from the tracker.
- **Acceptance criteria** as a checklist. This is what the plan will be graded on.
- **Attachments** — screenshots, exports, and mockups go in the sibling
  `attachments/` folder and are listed in the table. The planner cannot open
  external links, so paste anything that matters.
- **Out of scope** — the most valuable section. It prevents plan sprawl.

Rules of thumb: an intake describes *what and why*, never *how*. If you find
yourself naming C# types, that content belongs in **Technical hints**.

### 2. Plan — expensive, one pass

In Claude Code:

```
/squad-plan .squad/stories/<feature-slug>/<id>/intake.md
```

Or from the terminal:

```bash
squad new-plan .squad/stories/<feature-slug>/<id>/intake.md         # copy-paste mode
squad new-plan --api .squad/stories/<feature-slug>/<id>/intake.md   # direct API
```

Output: `.squad/plans/<feature-slug>/NN-story-<slug>[-<id>].md`, plus updated
`00-overview.md` and `00-index.md` rows.

A plan is acceptable only if it contains file paths, type and member signatures,
and runnable verification commands. "Consider adding validation" is a rejected
plan; "add `TicketTitle` value object in
`src/CrmTicketing.Domain/Tickets/TicketTitle.cs`, throw on length > 200" is an
accepted one.

Planning sessions do not touch application source. That separation is what makes
the plan reviewable.

### 3. Implement — cheap, repeatable

Open a **fresh, scoped session** and attach only the plan file. No repo tour, no
meta-prompt, no intake. The plan is the whole brief.

```bash
dotnet build CrmTicketing.slnx
dotnet test CrmTicketing.slnx
```

If the plan turns out to be wrong, stop and revise the plan — do not improvise in
the implementation session. That rule is Section I of
[the constitution](constitution.md).

## Useful commands

| Command | Purpose |
|---|---|
| `squad status` | Workspace summary |
| `squad list` | Stories and their plan state |
| `squad console` | Local web UI at `127.0.0.1:4571` |
| `squad doctor --fix` | Repair gitignore, permissions, missing dirs |
| `squad tracker link <story-path> <id>` | Attach a tracker id to an existing story |
| `squad rm` | Safely delete stories, plans, or whole features |
| `squad migrate` | Bring `.squad/` up to the current layout |
| `squad upgrade` | Update the CLI itself |

## Directory map

```
.squad/
├── config.yaml                     # project, tracker, agents, naming
├── secrets.yaml                    # git-ignored; created on demand
├── README.md                       # generated workspace readme
├── stories/
│   └── <feature-slug>/<id>/
│       ├── intake.md               # hand-written input
│       └── attachments/            # git-ignored binaries
└── plans/
    ├── 00-index.md                 # one row per feature
    └── <feature-slug>/
        ├── 00-overview.md          # one row per story, execution order
        └── NN-story-<slug>.md      # the executable artifact
```

`.claude/commands/` and `.github/prompts/` hold the generated agent entry points
(`/squad-plan`, `/squad-new-story`). They are regenerated by `squad init --force`
and should not be hand-edited.

## What CI enforces

`.github/workflows/ci.yml` runs two jobs:

- **build-and-test** — restore, build in Release with warnings as errors, test
  with coverage, publish the WebAssembly client.
- **sdd-guard** — `squad doctor`, plus a hard failure if `.squad/secrets.yaml`
  ever becomes tracked.
